# Story 1.2: Docker Compose Infrastructure Setup

## Status

Draft

## Story

**As a** system administrator,
**I want** Docker Compose configuration that orchestrates all services with single command,
**so that** I can deploy the entire system without manual service management.

## Acceptance Criteria

1. docker-compose.yml defines services: postgres, redis, api, watcher, worker, mailer
2. PostgreSQL service configured with persistent volume for data storage and health check
3. Redis service configured with persistent volume and health check
4. All application services configured with restart policies (unless-stopped)
5. Environment variables loaded from .env file into service containers
6. Network configuration allows inter-service communication (shared bridge network)
7. Volume mounts configured for scan folder and output folder access from host
8. Health check endpoints configured for all application services
9. docker-compose up command successfully starts all services with proper dependency ordering
10. docker-compose down cleanly stops all services without orphaned containers

## Dev Notes

### Docker Compose Architecture

[Source: architecture/deployment-architecture.md#L3-16]

- **Platform:** Docker Compose on self-hosted Linux VM or on-premises server
- **Build Command:** `docker-compose build` builds Docker images for all services
- **Deployment Method:** `docker-compose up -d` runs services in detached mode
- **Rationale:** Single-command deployment simplifies operations. No Kubernetes needed for MVP (<100 docs/day). Self-hosted keeps documents on-premises for compliance.

### Service Definitions

[Source: architecture/components.md]

Six services must be defined:

1. **postgres** - PostgreSQL 16 database with persistent storage
2. **redis** - Redis 7 cache/queue with append-only persistence
3. **api** - Express.js REST API (port 3000)
4. **watcher** - File monitoring service (port 3001)
5. **worker** - AI analysis worker (port 3002)
6. **mailer** - Email notification service (port 3003)

### PostgreSQL Configuration

[Source: architecture/database-schema.md, architecture/backend-architecture.md#L149-175]

- **Image:** postgres:16 (official image)
- **Persistence:** Named volume postgres_data mounted to /var/lib/postgresql/data
- **Health Check:** `pg_isready -U ${POSTGRES_USER}` every 10s
- **Connection Pool:** Max 20 connections (configured in API service)
- **Environment Variables:** POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD from .env

### Redis Configuration

[Source: architecture/tech-stack.md#L15, architecture/components.md]

- **Image:** redis:7-alpine (lightweight official image)
- **Persistence:** Named volume redis_data with append-only file (AOF) enabled
- **Purpose:** Queue + session cache + rate limiting
- **Health Check:** `redis-cli ping` every 10s
- **Connection:** Services connect via redis://redis:6379

### Restart Policies

[Source: architecture/deployment-architecture.md]

- **Application Services:** restart: unless-stopped (auto-restart on failure, manual stop persists)
- **Rationale:** Ensures services recover from crashes but respect manual shutdown
- **Database Services:** Same restart policy for consistency

### Environment Variables

[Source: architecture/coding-standards.md#L9, architecture/tech-stack.md]

- Load from .env file using env_file directive
- Each service receives same .env for consistency
- Critical variables: DATABASE*URL, REDIS_URL, GEMINI_API_KEY, SMTP*_, JWT\__, SCAN_FOLDER_PATH, OUTPUT_FOLDERS_BASE

### Network Configuration

[Source: architecture/deployment-architecture.md]

- **Network Type:** Custom bridge network (ai-scanner-network)
- **DNS Resolution:** Services reach each other by service name (e.g., postgres, redis)
- **CORS:** Frontend served by API eliminates CORS complexity
- **Example Connection Strings:**
  - Database: `postgresql://user:pass@postgres:5432/ai_scanner`
  - Redis: `redis://redis:6379`

### Volume Mounts

[Source: architecture/unified-project-structure.md, architecture/components.md]

**Scan Folder (Read-Only):**

- Watcher service: ${SCAN_FOLDER_PATH}:/mnt/scan-folder:ro
- Worker service: ${SCAN_FOLDER_PATH}:/mnt/scan-folder:ro (reads documents for analysis)
- Mailer service: ${SCAN_FOLDER_PATH}:/mnt/scan-folder:ro (reads for thumbnails)

**Output Folders (Read-Write):**

- API service: ${OUTPUT_FOLDERS_BASE}:/mnt/output-folders:rw (file move operations on approval)

**Data Persistence:**

- postgres_data volume (PostgreSQL data)
- redis_data volume (Redis AOF file)

### Health Checks

[Source: architecture/components.md]

All services expose GET /health endpoints:

- **API:** GET /health returns {status: "healthy", timestamp, version}
- **Watcher:** GET /health returns {status: "healthy", last_poll_timestamp}
- **Worker:** GET /health returns {status: "healthy", last_job_processed}
- **Mailer:** GET /health returns {status: "healthy", last_batch_sent}

Health check configuration:

- Interval: 30s for app services, 10s for databases
- Timeout: 5s
- Retries: 3-5 attempts
- Start Period: 40s (allows initialization time)

### Service Dependencies

[Source: architecture/deployment-architecture.md]

Startup order:

1. postgres, redis (no dependencies)
2. watcher, worker, api (depend on postgres + redis healthy)
3. mailer (depends on postgres + api healthy)

Use depends_on with condition: service_healthy to ensure proper ordering.

### Docker Compose Environments

[Source: architecture/deployment-architecture.md#L72-88]

- **Development:** docker-compose.dev.yml with hot reload, debug logs, exposed ports
- **Production:** docker-compose.prod.yml with optimized builds, resource limits, no debug

### CI/CD Integration

[Source: architecture/deployment-architecture.md#L18-70]

GitHub Actions workflow:

- Builds Docker images on push to main
- Pushes images to Docker Hub (optional for MVP)
- Manual deployment: SSH to server, `docker-compose pull && docker-compose up -d --no-deps --build`

### Project Structure for Docker

[Source: architecture/unified-project-structure.md#L81-84]

```
docker/
├── docker-compose.yml       # Main compose file
├── docker-compose.dev.yml   # Development overrides
└── docker-compose.prod.yml  # Production overrides
```

Each service will have Dockerfile in its service directory:

- services/watcher/Dockerfile
- services/worker/Dockerfile
- services/api/Dockerfile
- services/mailer/Dockerfile

(Dockerfiles created in future stories when services are implemented)

### Testing

[Source: architecture/testing-strategy.md]

Testing Docker Compose is manual for this story:

- Verify `docker-compose up -d` starts all services
- Check health status: `docker-compose ps`
- View logs: `docker-compose logs -f [service]`
- Test shutdown: `docker-compose down`
- Verify persistence: restart containers and check data remains
