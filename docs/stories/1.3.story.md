# Story 1.3: PostgreSQL Database Schema and Migrations

## Status

Draft

## Story

**As a** developer,
**I want** PostgreSQL database with initial schema for users, documents, and queue,
**so that** services have persistent storage for application state.

## Acceptance Criteria

1. Database migration tool (node-pg-migrate) configured in api service
2. Initial migration creates users table with fields: id, username, password_hash, created_at, updated_at
3. Initial migration creates documents table with fields: id, filename, scan_path, scan_timestamp, status, analysis_result (JSONB), destination_path, user_action, user_id, created_at, updated_at
4. Initial migration creates processing_queue table with fields: id, document_id, status, retry_count, error_message, created_at, updated_at
5. Indexes created on documents.status, documents.user_id, processing_queue.status
6. Database connection pooling configured with max 20 connections
7. Migration runs automatically on api service startup if not already applied
8. Connection string read from DATABASE_URL environment variable
9. Database connection failure results in service failing to start with clear error message

## Dev Notes

### Database Schema Design

[Source: architecture/database-schema.md]

The PostgreSQL schema includes 4 core tables:

**users table:**

- id UUID (primary key, auto-generated with uuid_generate_v4())
- username VARCHAR(255) UNIQUE NOT NULL
- password_hash VARCHAR(255) NOT NULL (bcrypt hash, never plaintext)
- created_at, updated_at TIMESTAMP

**documents table:**

- id UUID (primary key)
- filename, scan_path, scan_timestamp (file metadata)
- status enum: queued, processing, analyzed, filed, rejected, failed
- analysis_result JSONB (flexible schema for Gemini responses)
- destination_path TEXT (filled after approval)
- user_action enum: approved, rejected, edited (nullable)
- user_id UUID REFERENCES users(id) ON DELETE SET NULL
- notified BOOLEAN DEFAULT FALSE (for email batch tracking)
- created_at, updated_at TIMESTAMP

**processing_queue table:**

- id UUID (primary key)
- document_id UUID REFERENCES documents(id) ON DELETE CASCADE
- status enum: pending, processing, completed, failed
- retry_count INTEGER (max 3)
- error_message TEXT (nullable)
- created_at, completed_at TIMESTAMP

**batches table:**

- id UUID (primary key)
- document_ids UUID[] (array of document IDs for batch email)
- created_at, triggered_at, email_sent_at TIMESTAMP
- status enum: pending, triggered, sent, send_failed
- error_message TEXT (nullable)

### Database Connection Pool

[Source: architecture/backend-architecture.md#L149-175]

```typescript
// services/api/src/utils/db.ts
import { Pool } from 'pg';

export const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 20, // Maximum connections
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 2000,
});

pool.on('error', (err) => {
  logger.error({ err }, 'Unexpected database error');
  process.exit(-1); // Restart container on DB connection loss
});

export async function checkDbHealth(): Promise<boolean> {
  try {
    await pool.query('SELECT 1');
    return true;
  } catch (err) {
    logger.error({ err }, 'Database health check failed');
    return false;
  }
}
```

### Index Strategy

[Source: architecture/database-schema.md#L34-37, #L50-51, #L64]

**Performance Indexes:**

- idx_documents_status: Optimizes queries filtering by document status
- idx_documents_user_id: Optimizes queries for user's reviewed documents
- idx_processing_queue_status: Optimizes queue job queries
- idx_processing_queue_document_id: Optimizes lookups by document
- idx_batches_status: Optimizes batch processing queries

**Partial Index:**

- idx_documents_notified ON documents(notified) WHERE status='analyzed'
- Optimizes email service query: `WHERE status='analyzed' AND notified=false`
- Only indexes rows where status='analyzed' (reduces index size)

### Schema Design Notes

[Source: architecture/database-schema.md#L82-88]

- **JSONB for analysis_result:** Flexible schema for Gemini responses (field structure may evolve without migrations)
- **ON DELETE CASCADE for processing_queue:** When document deleted, related queue entries auto-deleted (cleanup)
- **ON DELETE SET NULL for user_id:** Preserve document records even if user account deleted (audit trail)
- **UUID primary keys:** Enable distributed ID generation, avoid sequential ID enumeration attacks
- **CHECK constraints:** Enforce valid enum values at database level (redundant with app validation for data integrity)

### Auto-Update Trigger

[Source: architecture/database-schema.md#L66-79]

Automatically update updated_at timestamp on row modification:

```sql
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = CURRENT_TIMESTAMP;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER update_users_updated_at BEFORE UPDATE ON users
    FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();

CREATE TRIGGER update_documents_updated_at BEFORE UPDATE ON documents
    FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();
```

### Connection String Format

[Source: architecture/tech-stack.md, architecture/backend-architecture.md]

DATABASE_URL environment variable format:

```
postgresql://username:password@host:port/database_name
```

For Docker Compose:

```
postgresql://postgres:postgres@postgres:5432/ai_scanner
```

### Error Handling

[Source: architecture/coding-standards.md#L21-22]

- Database connection errors must log with context and exit process
- Docker restart policy (unless-stopped) ensures service recovers when DB is ready
- Migration errors should fail fast with clear error messages

### Testing Strategy

[Source: architecture/testing-strategy.md]

Migration testing approach:

- Manual testing: docker-compose up verifies migration executes
- Check tables exist: `docker-compose exec postgres psql -c "\dt"`
- Check indexes: `docker-compose exec postgres psql -c "\di"`
- Test rollback: npm run migrate:down
- Test idempotency: running migrate:up multiple times should be safe

Integration tests (future stories) will use Vitest + Supertest to test database queries.
